# 行为准则

源自 Andrej Karpathy 对 LLM 编码陷阱的观察，约束 AI 的**工作方式**（HOW），与领域规则（WHAT）互补。

**权衡：** 这些准则偏向谨慎而非速度。对于简单任务（拼写错误、明显的一行修复），自行判断——并非每次改动都需要完整流程。

---

## 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

动手之前：
- 明确陈述你的假设。如果不确定，直接问。
- 如果存在多种理解，全部列出来——不要默默选择一种。
- 如果有更简单的方案，说出来。该反驳时反驳。
- 如果有不清楚的地方，停下来。指出困惑点。提出疑问。

```
❌ 错误：用户说「消息快一点」，就直接跳过权限校验 + 全量推送
✅ 正确：先问清楚——延迟来自接口、WS，还是通知？权限与扇出策略不可绕过
```

## 2. 简洁优先

**用最少代码解决问题。不过度推测。**

- 不加需求之外的功能
- 不为单次使用的代码创建抽象
- 不加未要求的「灵活性」或「可配置性」
- 不为不可能发生的场景写错误处理
- 能 50 行搞定的事不写成 200 行

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

**与项目规则的关系：** BlueDock 已有明确的模块边界（`bluedock-{domain}` / `bluedock-common` / Worker），这些是**必要的**架构约束。简洁优先原则适用于**这些边界之内**的代码——不要在单个 Service 或 Controller 内过度设计。

## 3. 精准修改

**只碰必须碰的。只清理自己造成的烂摊子。**

编辑已有代码时：
- 不要「顺手改进」相邻代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格，哪怕你觉得自己的写法更好
- 如果注意到无关的死代码，提一下——但不要删

**未使用引用（每次改完必清）：**
- 删除因本次改动而不再使用的 `import`（含 `import static`）、局部变量、私有方法
- 提交前扫一眼 IDE「未使用的 import」告警，或 `mvn compile` / `mvn test` 确认无红字
- **不要**为清 import 去删预先存在、与本次需求无关的死代码

**新增代码零告警（生产 + 单测）：**
- 本次新增或修改的文件，提交前 IDE **Problems** 不得残留 Warning
- **单测与生产代码同标准**
- SDK 泛型擦除等无法在调用点消除的告警 → 集中到 `bluedock-common` 工具类或模块内 `*TestSupport`，**一处** `@SuppressWarnings`

**检验标准：** 每一行修改都应该能直接追溯到用户的需求。

## 4. 目标驱动执行

**定义成功标准。循环执行直到验证通过。**

| 不要… | 转化为… |
| ---- | ------ |
| 「加个验证」 | 「先写无效输入测试 → 让测试通过」 |
| 「修这个 bug」 | 「先写复现测试 → 确认失败 → 修到通过」 |
| 「重构 X」 | 「确保重构前后 `mvn test` 全部通过」 |
| 「新增 API」 | 「对照 `docs/contract/api-contract.md` → 编译 → 测试」 |

多步骤任务先列计划：

```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
```

## 反模式速查

| 原则 | 反模式 | 修正 |
| ---- | ------ | ---- |
| 编码前思考 | 默默假设 API 路径、JSON 字段、表结构 | 明确列出假设，对照 `docs/contract/api-contract.md` |
| 简洁优先 | 单个通知渠道搞出庞大 Strategy 继承体系 | 一个 if/switch，等渠道 >3 个时再抽象 |
| 精准修改 | 修 bug 时顺手格式化整个文件；留下未使用 import | 只改需求相关行；删本次改动产生的孤儿 import |
| 目标驱动执行 | 「我来审查并改进代码」 | `mvn compile → mvn test`；本次改动文件 IDE 零 Warning |
